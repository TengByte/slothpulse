## 💡 What I Built

The first version of my standup assistant confidently described a user-supplied error as a failure in the assistant itself.

It had three neat headings. It sounded useful. It had invented the connection that mattered.

That became the interesting part of building **SlothPulse**: how much of a daily recap can I automate while keeping the result easy to question?

I work on production AI agent systems, and [my engineering notes](https://tengli.dev/) often return to the gap between a convincing demo and a tool someone can trust. For “Slow and Steady,” I picked a small, repetitive chore: turning Git history and a scattered terminal error into a standup draft. Reconstructing that context is exactly the kind of work I want to spend less attention on.

SlothPulse is a **local Python CLI using downloaded Gemma weights through Ollama**. It reads up to eight commits and an optional reported error, then creates three Markdown sections: completed work, blockers, and suggested next steps.

The useful detail is the receipt beside each item. A commit summary has a `C` source. A reported blocker and its investigation step share an `E` source. Python validates those bindings before the digest is saved. The model still needs a human editor, but the editor has a short route back to the input.

## 🛠️ How I Built It

The stack is deliberately small: `subprocess` for Git, `urllib.request` for Ollama, `json` for the contract, and Gemma for language. There is no framework or external Python package between the input and the saved note.

### Making source coverage part of the contract

Free-text Markdown gave the model control over both the prose and the structure. Tightening the wording helped, but it did not create a reliable boundary.

I changed the response to structured JSON. The first array-based design still omitted required evidence in local runs. Even a retry could fail. So I made the source IDs **required object keys**:

```json
{
  "completed": {
    "C1": "Fixed issue where export job IDs were lost during retries."
  },
  "blockers": {
    "E1": {
      "summary": "KeyError: 'result' while downloading job results.",
      "next_step": "Investigate the origin of the KeyError and potential data access issues in worker.py."
    }
  },
  "next_steps": []
}
```

This excerpt comes from the final response pattern. Python assigns the references from the keys; the model cannot silently replace a commit receipt with a made-up ID.

A later experiment revealed a subtler problem: an error investigation could cite an unrelated commit. Both IDs existed. Checking only whether a reference existed was insufficient. I now keep an error's summary and next step inside the same `E` object, then derive the two output sections from it.

The full pipeline is:

1. Collect a bounded Git window and optional errors.
2. Mask common credential patterns; let the user preview the exact evidence.
3. Inspect local model metadata before sending project context.
4. Ask Gemma for source-keyed JSON with an explicit schema.
5. Check required coverage and reference types; retry one invalid plan.
6. Render the three Markdown sections in Python and append a timestamp.

If validation fails twice, no digest is appended. An unavailable model produces a setup instruction rather than a fake success message.

### Local is a configuration, too

Ollama's local API can also front cloud-backed models. SlothPulse checks `/api/show` and rejects remote or unverifiable model metadata before sending the prompt. The tested server runs with `OLLAMA_NO_CLOUD=1`, and the client bypasses HTTP proxies. This trusts the local server; it is not a sandbox for arbitrary software.

### What I measured

On an **Apple M5 with 16 GB RAM**, Python 3.14.5, Ollama 0.40.8, and `gemma:latest` (`a72c7f4d0a15`), I ran each synthetic scenario three times:

| Scenario | Median process time | Final workflow checks |
| --- | ---: | --- |
| Five commits + one error | 7.668 s | 3/3 passed |
| Five commits only | 6.495 s | 3/3 passed |
| Error only, no repository | 3.926 s | 3/3 passed |

All nine final calls passed on their first attempt. The checks cover output structure, expected scope, source IDs, masking the fake credential, and saving. **They do not measure factual accuracy.** This is a small ordered batch with locally available weights, not a controlled cold-start benchmark. The repository includes the raw timings and earlier failure decisions.

There are also **23 unit tests** for boundaries such as unknown references, missing coverage, invalid output, cloud-model rejection, proxy bypass, preview behavior, and timestamped appends. Codex assisted with implementation, tests, demo preparation, and this article; the product's inference runs through local Gemma.

## 🔒 Why Does Open Innovation Matter?

Commit messages and stack traces can reveal internal project names, endpoints, and credentials. Open-weight Gemma lets this workflow run where that context already lives. After the initial model download, the CLI needs no hosted inference account, API key, or prompt upload to a cloud model.

That also makes the workflow inspectable. Anyone can read the collector, replace the model, reproduce the fixture, or improve the validator. The important boundary is visible in ordinary Python rather than hidden behind a service.

Local processing does not make the output automatically safe to publish. Masking is best effort; preview it. The saved report can still contain confidential context. And a source reference proves that an input existed, not that the interpretation is true. Those are limits I want users to see before they rely on the draft.

## 🦥 The Lazy Payoff

The payoff is starting with a reviewable draft instead of reconstructing the same context into an empty text box. Pick a window, supply the relevant error, run one command, and edit the Markdown.

I have measured generation latency, not a person's weekly time savings. I cannot honestly turn “roughly four to eight seconds in these median runs” into “15 minutes saved.” The useful next evaluation is whether people spend less effort correcting a source-linked draft than writing one themselves.

For now, SlothPulse removes a small formatting and recall chore while leaving the judgment visible. That feels like the right amount of laziness to automate.
